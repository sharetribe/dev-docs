# Modify booking time intervals in time-based listings

In Sharetribe, listings can have either day-based or time-based
availability. For listings with time-based availability, the available
[time slots](https://www.sharetribe.com/api-reference/marketplace.html#time-slots)
are returned from the API as continuous stretches of time. The client
application must therefore split the availability into suitable booking
lengths.

The default behavior of the Sharetribe Web Template hourly listings is
to split the continuous availability stretch into one hour bookable
intervals. This how-to guide illustrates a handful of different cases on
modifying booking lengths. These changes apply to all listings where the
unit type is set to "hour".

<Callout type="info">

The Sharetribe Web Template also supports fixed timeslots, where the
provider can choose the length of possible bookings, and the customer
only selects a start time for their booking. This guide applies to
non-fixed time slots, where the customer can select multiple intervals
of the available booking length by setting a start time and an end time.

This guide builds on top of release
[v12.5.0](https://github.com/sharetribe/web-template/releases/tag/v12.5.0).
If you are working on an earlier version, you will need to apply some of
the changes from that version to support this use case in your template.

</Callout>

## Set booking length to 30 minutes

The simplest use case is to create uniform 30 minute booking slots
instead of hour long slots.

## Use an irregular time slot

If your booking length does not divide an hour evenly, such as 45 or 75
minutes, you will need a few more changes. In this example, we use a 45
minute booking length.

The template rounds custom time units to multiples of the unit length.
For a 45 minute unit, those multiples do not line up with full hours. As
a result, depending on the start time of the availability (8 AM vs 9 AM
vs 10 AM), the first time slot may start 15 or 30 minutes after the
actual start time.

To fix this, we round to a shorter interval that does line up with full
hours. To find that interval, we calculate the greatest common factor of
the booking length and a full hour using the
[Euclidean algorithm](https://en.wikipedia.org/wiki/Euclidean_algorithm).
For a 45 minute booking length, the greatest common factor with an hour
is 15 minutes. We then make sure that the first time slot starts at the
first 15 minute mark of the availability.

Then, let's add a helper function `gcf` for the greatest common factor,
and a constant for the length of an hour in minutes. We can add them
right after the comment that lists the functions to modify for custom
time units.

{/* prettier-ignore */}
```jsx filename="src/util/dates.js" {9-13}
// NOTE: If your customization is using different time-units than hours
// and different boundaries than sharp hours, you need to modify these functions:
// - findBookingUnitBoundaries (DST changes)
// - findNextBoundary
// - getSharpHours -> use getUnitBoundaries
// - getStartHours -> use getStartBoundaries
// - getEndHours -> use getEndBoundaries

const HOUR_MINUTES = bookingTimeUnits.hour.timeUnitInMinutes;

// Calculate the greatest common factor of two numbers
// using the Euclidean algorithm, e.g. gcf(45, 60) === 15
const gcf = (a, b) => (a ? gcf(b % a, a) : b);
```

Next, we'll modify the `findNextBoundary` function. It calculates each
boundary by adding the unit length to the previous boundary, and then
rounding down to a multiple of the unit length.

We make two changes to how it handles custom time units:

- We round to the greatest common factor of the unit length and an hour,
  instead of the unit length itself.
- We add an `isFirst` parameter. For the first boundary, we add the
  rounding length instead of the unit length. This moves the first
  boundary to the first 15 minute mark of the availability.

{/* prettier-ignore */}
```jsx filename="src/util/dates.js" {1,9-12,18}

  const customTimeUnitConfig = bookingTimeUnits[timeUnit]?.isCustom
    ? bookingTimeUnits[timeUnit]
    : null;

  if (!!customTimeUnitConfig) {
    // If the time unit is custom, we need to use startOfMinuteBasedInterval function to adjust 00, 15, 30, 45 rounding.

    return moment(currentDate)
      .clone()
      .tz(timeZone)
      .add(minuteOffset, 'minute')
      .startOfMinuteBasedInterval(roundingInMinutes)
      .toDate();

```

## Add separate handling for first timeslot

Sometimes, there are cases where you want to have a basic length for a
booking and then different lengths for subsequent time slots. For
instance, a listing could feature a 75 minute default bike rental with
the option to extend it for 30 minutes at a time. In those cases, you
need to create different handling for the first time slot, i.e. the
first start and end boundaries.

This section builds on the previous section. We add a time unit that has
two lengths: 75 minutes for the first time slot and 30 minutes for each
extension. Then we use the two lengths in the booking form:

- Start times are 30 minutes apart, and each start time needs at least
  75 minutes of availability after it.
- The first end time is 75 minutes after the start time. Each end time
  after that is 30 minutes later.

### Add a new custom unit and first unit handling to dates.js

<FileTree>
  <FileTree.Folder name="src" defaultOpen>
    <FileTree.Folder name="util" defaultOpen>
      <FileTree.File name="dates.js" />
    </FileTree.Folder>
  </FileTree.Folder>
</FileTree>

First, let's add a new time unit to `bookingTimeUnits`. The
`timeUnitInMinutes` value is the length of each extension, and the new
`firstUnitInMinutes` value is the length of the first time slot.

{/* prettier-ignore */}
```jsx filename="src/util/dates.js" {6-11}
  fortyFiveMinutes: {
    timeUnit: 'fortyFiveMinutes',
    timeUnitInMinutes: 45,
    isCustom: true,
  },
  customRental: {
    timeUnit: 'customRental',
    timeUnitInMinutes: 30,
    firstUnitInMinutes: 75,
    isCustom: true,
  },
};
```

Next, we need to include the first time slot length in the rounding. The
first end time of a booking is 75 minutes after its start time. For that
end time to fall on a rounding boundary, the rounding length needs to
divide 75 minutes as well as the extension length and an hour. For a 75
minute first slot and 30 minute extensions, the rounding length is 15
minutes.

{/* prettier-ignore */}
```jsx filename="src/util/dates.js" {4-6}
  if (!!customTimeUnitConfig) {
    // If the time unit is custom, we need to use startOfMinuteBasedInterval function to adjust 00, 15, 30, 45 rounding.
    const customTimeUnitInMinutes = customTimeUnitConfig?.timeUnitInMinutes;
    const firstUnitInMinutes = customTimeUnitConfig?.firstUnitInMinutes || 0;
    // Round to an interval that lines up with full hours and the first time slot length, e.g. 15 minutes for 75 and 30 minute units
    const roundingInMinutes = gcf(gcf(customTimeUnitInMinutes, HOUR_MINUTES), firstUnitInMinutes);
```

Time units without `firstUnitInMinutes` round the same way as before,
because the greatest common factor of any number and 0 is the number
itself.

The `getStartBoundaries` and `getEndBoundaries` functions assume that
start and end times are one time unit apart. `getStartBoundaries`
removes the last boundary, and `getEndBoundaries` removes the first one.
With a longer first time slot, we need to filter the boundaries
ourselves. So we replace both imports with `getUnitBoundaries`, which
returns every boundary in the given range.

```jsx filename="src/components/OrderPanel/BookingTimeForm/FieldDateAndTimeInput.js" {2}

```

Then, let's update the start times in `getAvailableStartTimes`. We keep
the start times that leave room for the first time slot before the
availability ends. The `endLimit` check removes the boundary at
midnight, which belongs to the next day.

{/* prettier-ignore */}
```jsx filename="src/components/OrderPanel/BookingTimeForm/FieldDateAndTimeInput.js" {5-9}

    // Start times need enough availability for the first time slot

    );
    return availableHours.concat(hours);
  }, []);
  return allHours;
```

Next, we'll update the end times in `getAvailableEndTimes`. The first
end time is the first time slot length after the booking start. From
there, `getUnitBoundaries` adds 30 minutes at a time. When the customer
selects an end date after the start date, the filter keeps only the end
times on that date.

```jsx filename="src/components/OrderPanel/BookingTimeForm/FieldDateAndTimeInput.js" {8-12}
      : dayAfterBookingEnd;

  // The first end time is the first time slot length after the booking start
  const firstEndTime = getStartOf(bookingStartTimeAsDate, 'minute', timeZone, duration.firstUnitInMinutes, 'minutes');
```
